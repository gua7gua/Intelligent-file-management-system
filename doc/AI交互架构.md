# 1. 核心原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | AI 只看元数据 | AI 输入限于文件名、清单字段、用户填写的说明、档案元数据，不读取文档正文 |
| 2 | AI 不直接写库 | AI 只返回结构化 JSON 建议或规则，不直接新增、修改、删除数据库记录 |
| 3 | AI 不覆盖业务判断字段 | 密级、保管期限、是否公开、是否允许数字化等字段由移交单位或审批流程决定，AI 不得覆盖 |
| 4 | AI 输出必须白名单过滤 | 后端只接收允许字段，出现受保护字段时剥离或拒绝 |
| 5 | AI 结果必须人工确认 | 元数据补全、检索条件、分类研判都需要用户确认后才进入后续操作 |
| 6 | 权限校验在后端完成 | AI 生成的规则或建议不能绕过 Sa-Token、角色、密级和数据范围校验 |
| 7 | AI 不作为主流程依赖 | AI 不可用时，系统回退到手工填写和手工筛选，核心业务不能阻塞 |
| 8 | 不使用 RAG / 向量数据库 | 本期不做文档正文向量化检索，不引入向量数据库 |
| 9 | 只提供固定 AI 入口 | 本期只做内部检索、公众检索、档案研判、接收清单补全 4 个入口 |

# 2. AI 交互基本模式

## 2.1 统一流程

AI 在本系统中分为两类调用模式：**同步检索 JSON 生成**和**异步批处理建议生成**。无论哪种模式，都不允许 AI 直接执行最终业务操作。

```text
用户触发 AI 功能
    ↓
系统注入必要上下文
    ↓
AI 返回结构化 JSON
    ↓
后端解析 JSON 并做白名单过滤
    ↓
前端展示建议或规则
    ↓
用户检查、修改、确认
    ↓
后端按当前用户权限和业务状态执行
    ↓
记录操作日志
```

内部检索和公众检索属于同步调用；接收清单补全和档案研判属于异步批处理任务。二者都必须经过系统校验和用户确认。

## 2.2 AI 交互区 UI 形态

AI 交互采用轻量形态，不把 AI 做成复杂页面协作者。

- 入库场景：按钮触发 AI 补全，页面展示字段对照和 JSON 原始结果。
- 检索场景：自然语言输入区生成查询 JSON，用户确认后填充筛选表单。
- 数据研判场景：后台批量扫描，AI 返回异常候选清单，管理员确认后处理。

## 2.3 固定使用场景

本期 AI 只用于以下 4 个入口：

| # | 场景 | 调用模式 | 输入 | 输出 |
|---|------|----------|------|------|
| 1 | 内部检索 | 同步 | 用户自然语言、固定分类、当前用户可见标签集合 | 检索表单 JSON |
| 2 | 公众检索 | 同步 | 用户自然语言、固定分类、公开档案标签集合 | 公开检索表单 JSON |
| 3 | 档案研判 | 异步批处理 | 正式档案元数据，默认每批 50 条 | 异常候选 JSON |
| 4 | 接收清单补全 | 异步批处理 | 已接收清单条目元数据，默认每批 50 条 | 字段建议 JSON |

不在上述 4 个入口内的页面，不提供 AI 能力。

## 2.4 JSON 结果处理

AI 响应必须使用 `<JSON>` 标签包裹结构化内容。

```text
<JSON>
{
  "ruleType": "fieldCompletion",
  "items": []
}
</JSON>
```

后端只提取第一组 `<JSON></JSON>` 中的内容，并执行：

- JSON 格式校验
- `ruleType` 校验
- 字段白名单校验
- 枚举值校验
- 当前业务状态校验
- 当前用户权限校验
- 目标 ID 归属校验，确保 AI 只能返回本次请求中的条目或档案 ID

## 2.5 同步检索调用

内部检索和公众检索只负责把自然语言转换成表单字段，不直接查询数据库。

调用流程：

```text
用户输入自然语言
    ↓
后端查询固定分类和当前用户可见标签集合
    ↓
组装提示词并调用 AI
    ↓
提取并校验 JSON
    ↓
校验通过则返回表单 JSON
    ↓
用户确认后调用普通检索接口
```

检索提示词不注入档案题名，因为题名数量过大。标签集合由后端按当前用户可见范围过滤后去重生成：内部用户必须同时受密级上限、所属单位或全宗范围、档案生命周期约束，内部用户不按 `open_status` 过滤；公众用户只能使用非密、公开、正常状态档案的标签。

检索类 JSON 校验失败时，后端最多重新调用 AI 3 次。3 次仍失败时，接口返回 AI 服务异常，页面提示用户稍后重试或改用普通筛选。

## 2.6 异步批处理调用

档案研判和接收清单补全按批处理执行，默认每批 50 条。批大小通过系统配置控制，接口可使用默认值，不需要前端传入。

批处理流程：

```text
管理员创建 AI 任务
    ↓
后端按默认批大小拆分目标数据
    ↓
逐批调用 AI
    ↓
每批独立校验 JSON
    ↓
成功批次写入建议结果
    ↓
失败批次记录错误
    ↓
汇总任务状态
```

AI 任务状态：

| 状态 | 说明 |
|------|------|
| `running` | 任务执行中 |
| `partial_completed` | 部分批次成功，存在失败批次 |
| `completed` | 全部批次成功 |
| `failed` | 全部批次失败或任务无法启动 |

AI 批次状态：

| 状态 | 说明 |
|------|------|
| `pending` | 等待执行 |
| `running` | 当前批次调用中 |
| `success` | 当前批次 JSON 校验通过并已写入建议 |
| `failed` | 当前批次调用失败或 JSON 校验失败 |

当任务为 `partial_completed` 时，页面展示成功批次数、失败批次数和错误摘要。管理员点击“重试失败批次”时，后端只重试 `failed` 批次；全部失败批次成功后，任务状态变为 `completed`。

# 3. 上下文注入机制

每次 AI 调用只注入完成当前任务必要的信息。

## 3.1 用户身份与权限上下文

| 注入字段 | 说明 |
|----------|------|
| `userRole` | 当前用户角色，如 `front_archivist`、`back_archivist`、`director`、`public_user`、`transfer_user`、`internal_reader` |
| `permissions` | 当前用户拥有的权限标识；本期可由角色推导 |
| `maxSecurityLevel` | 当前用户可访问的最高密级 |
| `currentPage` | 当前页面，如 `transfer-list-detail`、`archive-search`、`data-analysis` |
| `organizationId` | 当前用户所属单位或全宗范围 |

这些上下文只帮助 AI 少生成无效结果，不作为安全屏障。真正的安全控制必须在后端接口层完成。

## 3.2 分类与标签上下文

系统注入固定五大分类和当前用户可见标签集合。

```text
可用分类：
- 文书档案
- 科技档案
- 会计档案
- 音像档案
- 人事档案
```

标签按当前用户权限过滤后去重生成。内部用户按密级上限、所属单位或全宗范围、档案生命周期过滤，不按 `open_status` 过滤；公众用户只使用非密、公开、正常状态档案的标签。标签通常明显少于题名，本期不额外限制标签数量。

## 3.3 清单字段上下文

AI 补全入库字段时，只注入清单条目的已有字段，例如：

- 清单条目 ID
- 档案标题
- 档案文件名
- 档案形成日期
- 载体状态
- 页数
- 移交单位
- 移交部门
- 经办人
- 密级
- 保管期限
- 是否公开

其中密级、保管期限、是否公开等字段只能作为上下文参考，不能出现在 AI 可写入字段中。

# 4. AI 提示词设计

## 4.1 场景一：移交/征集清单批次字段补全

```text
你是档案管理系统的 AI 助手，帮助档案管理员从清单已有字段中补全正式入库所需的元数据。

约束：
- 你只能根据清单字段、文件名、移交单位、移交部门等元数据推测。
- 你不能读取电子文件正文。
- 你不能覆盖密级、保管期限、是否公开、是否允许数字化等业务判断字段。
- 分类必须从系统给定分类中选择。
- 标签优先从系统给定标签中选择，必要时可建议新增标签。
- 每次请求最多处理 50 条清单条目。
- 输出必须是 JSON，并使用 <JSON> 标签包裹。

允许补全字段：
- title
- responsible
- formedDate
- category
- tags

输出格式：
<JSON>
{
  "ruleType": "fieldCompletion",
  "items": [
    {
      "listItemId": "清单条目 ID",
      "fields": {
        "title": "正式题名",
        "responsible": "责任者",
        "formedDate": "yyyy-MM-dd",
        "category": "分类名称",
        "tags": ["标签1", "标签2"]
      }
    }
  ]
}
</JSON>
```

## 4.2 场景二：自然语言检索转查询条件

```text
你是档案管理系统的 AI 助手，将用户的自然语言检索需求转换为结构化查询条件。

约束：
- 分类必须从系统给定分类中选择。
- 标签必须优先从系统给定的可见标签集合中选择。
- 日期格式统一为 yyyy-MM-dd。
- 如用户为公众用户，必须附加 securityLevel = 0 且 openStatus = "open"。
- 你只生成查询条件，不执行查询。

输出格式：
<JSON>
{
  "ruleType": "query",
  "fields": {
    "keywords": ["关键词1", "关键词2"],
    "category": "分类名称",
    "formedDateRange": ["yyyy-MM-dd", "yyyy-MM-dd"],
    "responsible": "责任者",
    "securityLevelMax": 0,
    "openStatus": "open",
    "carrierStatus": "electronic / paper_electronic / paper"
  }
}
</JSON>
```

## 4.3 场景三：数据研判

```text
你是档案管理系统的 AI 助手，检查档案元数据是否存在明显分类不一致或字段缺失问题。

约束：
- 不确定的情况不要标记异常。
- 只返回候选异常，不直接修改档案。
- 每批最多处理 50 条档案。

输出格式：
<JSON>
{
  "ruleType": "dataAnalysis",
  "anomalies": [
    {
      "archiveId": "档案 ID",
      "issueType": "category_conflict / missing_field",
      "issue": "问题描述",
      "suggestion": "处理建议"
    }
  ]
}
</JSON>
```

# 5. 各页面 AI 交互实现

## 5.1 AI 应用场景总览

| 页面 | AI 能力 | 输入 | 输出 | 是否主流程必需 |
|------|---------|------|------|----------------|
| 移交清单详情 | 批量补全入库字段 | 清单字段、文件名、来源单位 | 字段建议 JSON | 否 |
| 征集清单详情 | 批量补全入库字段 | 捐赠清单字段、文件名、捐赠说明 | 字段建议 JSON | 否 |
| 后台入库页 | 查看并确认 AI 补全结果 | 清单条目和补全结果 | 人工确认后的入库字段 | 否 |
| 内部检索页 | 自然语言转查询条件 | 用户检索描述 | 查询条件 JSON | 否 |
| 公众检索页 | 自然语言转公开查询条件 | 用户检索描述 | 强制公开条件的查询 JSON | 否 |
| 数据研判页 | 分类一致性与完整性扫描 | 档案元数据 | 异常候选清单 | 否 |

## 5.2 移交/征集清单详情

管理员在清单已接收或部分接收后，点击「AI 补全」。AI 只对已接收条目生成候选字段，不处理已回退条目。

处理流程：

```text
清单条目进入后台待入库
    ↓
管理员点击 AI 补全
    ↓
系统按默认 50 条拆分批次
    ↓
AI 返回允许字段
    ↓
后端白名单过滤
    ↓
页面展示清单原始字段和 AI 候选字段
    ↓
管理员逐条确认或修改
    ↓
点击入库后生成正式档案
```

## 5.3 检索页

内部用户和公众用户都可以使用自然语言检索，但返回范围不同。

- 内部用户：按角色、密级、所属单位或全宗范围过滤。
- 公众用户：后端强制追加 `securityLevel = 0` 和 `openStatus = open`。

AI 只负责生成查询条件，不返回数据库结果，不生成 MinIO 访问地址。

## 5.4 数据研判页

数据研判用于帮助管理员发现元数据问题，不自动修改正式档案。典型检查包括：

- 必填字段缺失
- 分类与题名明显不一致
- 保管期限即将到期
- 载体状态与文件/架位信息不一致

其中保管期限到期的处理仍进入鉴定流程，AI 不直接决定延长或销毁。

# 6. 安全边界

## 6.1 AI 禁止操作

| 禁止操作 | 说明 |
|----------|------|
| 直接写入数据库 | 所有写入必须由后端业务接口执行 |
| 覆盖受保护字段 | 密级、保管期限、是否公开、是否允许数字化不可由 AI 覆盖 |
| 读取电子文件正文 | 本期 AI 不接触 MinIO 文件内容 |
| 绕过权限 | AI 规则执行仍必须经过后端鉴权 |
| 直接删除文件 | 文件删除只发生在销毁流程确认后，由后端按审计规则执行 |
| 直接生成档号 | 档号由系统入库逻辑生成，AI 不参与 |

## 6.2 后端白名单

AI 字段补全只允许以下字段进入候选结果：

| 字段 | 说明 |
|------|------|
| `title` | 正式题名 |
| `responsible` | 责任者；后端确认后落库到 `confirmed_responsible_text` / `archives.responsible_text` |
| `formedDate` | 形成日期 |
| `category` | 分类 |
| `tags` | 标签 |

出现以下字段时必须剥离或拒绝：

- `securityLevel`
- `retentionPeriod`
- `openStatus`
- `allowDigitization`
- `archiveNo`
- `warehouseLocation`
- `destructionStatus`

# 7. 错误处理

## 7.1 AI 服务错误

| 错误场景 | 系统表现 | 用户操作 |
|----------|----------|----------|
| AI 服务超时 | 提示 AI 分析超时 | 可重试或手工填写 |
| AI 服务不可用 | 隐藏或禁用 AI 按钮 | 继续手工流程 |
| 未配置 API Key | 提示 AI 未配置 | 继续手工流程 |
| AI 返回格式不合法 | 提示结果格式异常 | 可重试或手工填写 |
| AI 返回受保护字段 | 剥离字段或拒绝本次结果 | 管理员手工处理 |

## 7.2 规则执行错误

| 错误场景 | 错误码 | 用户表现 |
|----------|--------|----------|
| 权限不足 | 403 | 提示无权执行此操作 |
| JSON 字段不完整 | 400 | 提示缺失字段 |
| 枚举值非法 | 400 | 提示字段值不在允许范围 |
| 业务状态不允许 | 409 | 提示当前状态不可执行 |
| AI 结果命中保护字段 | 422 | 提示 AI 结果包含不可修改字段 |
