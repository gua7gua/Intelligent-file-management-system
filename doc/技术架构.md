# 档案馆智能档案管理系统 - 技术架构

> 本文档描述系统的技术选型、分层设计、部署架构、安全设计、AI 服务对接和文件上传入库方案。当前版本以 `new-doc/业务场景.md` 的新业务流程为准。

## 1. 技术栈

| 层次 | 组件 | 方案 | 说明 |
|------|------|------|------|
| 后端框架 | Spring Boot | 3.x | 单体应用，承载业务接口 |
| Java 版本 | JDK | 17+ | 使用 LTS 版本 |
| ORM 框架 | MyBatis-Plus | 3.5.x | 适合复杂多表查询 |
| 权限认证 | Sa-Token | 1.40+ | 登录认证、角色权限、会话管理 |
| 数据库 | PostgreSQL | 17 推荐，16+ 最低 | 存储档案元数据、业务流程、日志 |
| 数据库迁移 | Flyway | 10+ | 版本化管理建表、索引、扩展和初始化字典 |
| 检索增强 | PostgreSQL `pg_trgm` + GIN/GiST 索引 | 数据库扩展 | 题名、责任者、档号、文件名的模糊检索 |
| 文件存储 | MinIO | S3 兼容对象存储 | 存储电子文件、扫描件、照片附件 |
| 文件类型识别 | Apache Tika | 3.x | 基于文件头和文件名识别 MIME 类型 |
| 病毒扫描 | ClamAV | 必选容器 | 电子文件上传安全性检查，作为四性检查的安全性环节 |
| 前端框架 | Vue | 3.x | 多门户前端 |
| UI 组件库 | Element Plus | 2.x | 表格、表单、弹窗、抽屉 |
| 前端构建 | Vite | 7.x | 前端构建工具，Node.js 使用 20.19+ 或 22.12+ |
| 前端状态 | Pinia + Vue Router + Axios | - | 门户路由、登录状态、权限菜单、接口请求 |
| 接口文档 | springdoc-openapi | 2.x | 自动生成 OpenAPI / Swagger UI，便于联调 |
| 参数校验 | Jakarta Validation | Spring Boot Starter Validation | DTO 参数校验 |
| 后台任务 | Spring TaskScheduler / ThreadPoolTaskExecutor | Spring 内置 | 批量四性检查、超期提醒、临时文件清理 |
| 监控健康 | Spring Boot Actuator | 3.x | 健康检查、指标、任务和迁移状态观测 |
| Excel 导入导出 | FastExcel | 1.x | 清单导入、清册导出、统计表导出 |
| PDF 导出 | OpenHTMLToPDF + PDFBox | 1.x | 移交清单、接收回执、审批凭证 PDF |
| AI API | DeepSeek / OpenAI 兼容接口 | 可配置 | API Key 通过环境变量注入 |
| 短信服务 | 阿里云短信 | 可选 | 公众用户手机验证码登录或找回密码 |
| 部署 | Docker + docker-compose | - | 课程项目和小规模部署友好 |
| Web 服务器 | Nginx | 1.24+ | 反向代理和静态资源托管 |

关键取舍：

- 不使用微服务，当前规模单体 Spring Boot 足够。
- 不引入 Redis，先用 PostgreSQL 支撑会话外业务数据。
- 不引入消息队列，批量检查本期同步或后台任务即可。
- 不使用 RAG 和向量数据库，AI 不读取正文。
- 不引入 Elasticsearch，先用 PostgreSQL B-tree、`pg_trgm` 和必要的组合索引支撑元数据检索。
- ClamAV 作为必接组件，Spring Boot 通过 `clamd` TCP 3310 调用；开发环境仅绑定 `127.0.0.1`，生产环境只允许容器内网访问，不对公网暴露扫描端口。

### 1.1 技术栈落地优先级

| 优先级 | 技术栈 | 落地口径 |
|--------|--------|----------|
| 必选 | Flyway、Jakarta Validation、springdoc-openapi、Pinia、Vue Router、Axios | 支撑数据库演进、接口联调和前端基础工程 |
| 必选 | PostgreSQL 索引、`pg_trgm`、Apache Tika、FastExcel、OpenHTMLToPDF | 支撑检索、文件四性检查、清单/回执导出 |
| 建议 | Spring Boot Actuator、Spring TaskScheduler / ThreadPoolTaskExecutor | 支撑健康检查、临时文件清理、批量研判和异步任务 |
| 可选 | Redis、Elasticsearch、预签名直传 | 正式部署或规模扩大后启用；本期不作为主流程依赖 |

## 2. 分层架构

系统采用前后端分离的单体后端架构。

1. **客户端层**

   四个门户：

   - 公众门户 `/public/*`
   - 内部查阅者门户 `/internal/*`
   - 移交单位门户 `/transfer/*`
   - 管理后台 `/admin/*`

2. **网关层**

   Nginx 负责静态资源托管和 API 转发。

   - `/api/*` 转发至 Spring Boot
   - 其他路径返回 Vue 构建产物

3. **应用服务层**

   单体 Spring Boot 应用，包含 Controller、Service、Mapper、权限认证、AI Client、文件处理和审计日志。

4. **数据存储层**

   - PostgreSQL：档案元数据、清单、批次、审批、借阅、库房、销毁、日志
   - MinIO：电子文件、扫描件、销毁现场照片、回执附件等

### 2.1 各层职责

**前端层：**

- 按门户拆分路由和菜单
- 使用统一表格、表单、弹窗、抽屉、上传组件
- 清单侧拖拽文件只解析文件名，不上传文件本体
- 前台接收页面负责真实文件上传和匹配结果展示
- AI 结果只展示为候选字段或查询条件，最终提交仍走业务接口

**应用服务层：**

- Controller：参数接收、基础校验、响应封装
- Service：业务流程编排、状态流转、事务控制
- Mapper：MyBatis-Plus 数据访问
- AuthContext：封装当前用户、角色、权限、密级、单位和数据范围
- FileService：文件校验、哈希计算、MinIO 上传、暂存转正式
- AiSuggestionService：AI 调用、JSON 提取、白名单过滤
- AiTaskService：AI 批处理任务拆分、批次状态汇总、失败批次重试
- AuditService：关键操作日志记录

**数据存储层：**

- PostgreSQL 管正式业务数据，MinIO 管文件本体
- 文件路径、哈希、格式、大小和状态必须落库
- 删除电子文件时仍保留档案元数据、销毁清册、审批记录和操作日志

### 2.2 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 架构形态 | 单体 Spring Boot | 毕业设计和中小馆部署场景更易落地 |
| 权限框架 | Sa-Token | 配置轻量，适合角色和权限控制 |
| 数据访问 | MyBatis-Plus | 便于写复杂筛选和统计 SQL |
| 文件存储 | MinIO | 与对象存储兼容，适合电子档案 |
| AI 边界 | 元数据建议和查询规则 | 不读取正文，不绕过权限 |
| 文件接收 | 前台统一上传 | 避免移交单位账号泄露导致恶意上传 |
| 入库路径 | 先暂存，入库后转正式 | 接收阶段没有正式档号，不提前占用 |

## 3.1 接口统一约定

后端接口统一以 `/api` 为前缀，接口文档由 springdoc-openapi 生成。Controller 负责参数校验和响应封装，业务状态、权限、数据范围和状态流转校验统一放在 Service 层。

### 3.1.1 响应结构

普通 JSON 接口统一返回：

```json
{
  "code": "OK",
  "message": "success",
  "data": {},
  "traceId": "请求追踪 ID"
}
```

约定：

- `code = OK` 表示成功；失败时使用稳定错误码，不直接把异常类名返回给前端。
- `message` 用于页面提示，默认中文；前端不依赖 `message` 做逻辑判断。
- `traceId` 由后端过滤器生成并写入日志，便于排查上传、AI、导出等链路问题。
- 文件下载、PDF 导出和预签名跳转类接口可直接返回文件流或下载 URL，但失败时仍返回统一错误结构。

### 3.1.2 分页结构

管理列表默认使用页码分页：

```json
{
  "records": [],
  "pageNo": 1,
  "pageSize": 20,
  "total": 100,
  "hasNext": true
}
```

参数约定：

- `pageNo` 从 1 开始，默认 1。
- `pageSize` 默认 20，普通列表最大 100；导出接口不复用分页接口，单独走导出任务或流式导出。
- 排序字段只能使用后端白名单，禁止前端直接传数据库字段拼接 SQL。
- 大批量日志、审计、访问记录可使用游标分页，参数为 `cursor`、`limit`，返回 `nextCursor` 和 `hasNext`。

### 3.1.3 错误码

| HTTP 状态 | `code` | 使用场景 |
|-----------|--------|----------|
| 400 | `BAD_REQUEST` | 参数格式错误、缺少必填字段、枚举值非法 |
| 401 | `UNAUTHORIZED` | 未登录或 token 无效 |
| 403 | `FORBIDDEN` | 角色、密级或数据范围不足 |
| 404 | `NOT_FOUND` | 业务对象不存在或当前用户不可见 |
| 409 | `BUSINESS_CONFLICT` | 当前状态不允许操作、重复借阅、重复审批、架位已占用 |
| 413 | `PAYLOAD_TOO_LARGE` | 上传文件超过配置上限 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | 文件格式或 MIME 类型不允许 |
| 422 | `VALIDATION_FAILED` | AI 结果包含不可用字段、业务规则校验不通过 |
| 429 | `TOO_MANY_REQUESTS` | 登录、短信验证码、AI 调用等触发限流 |
| 500 | `INTERNAL_ERROR` | 未预期系统错误 |
| 502 | `EXTERNAL_SERVICE_ERROR` | AI、MinIO、ClamAV、短信等外部服务异常 |

上传接收阶段 ClamAV 不可用、扫描超时、扫描失败或命中病毒时，接口返回失败，不创建 `staging_files` 或 `business_attachments` 等可用文件记录。失败原因写入 `audit_logs`。命中病毒优先返回 `VALIDATION_FAILED`，扫描服务不可用或超时返回 `EXTERNAL_SERVICE_ERROR`。

### 3.1.4 枚举和展示文本

数据库只保存英文枚举。接口返回业务对象时可以同时返回 `status` 和 `statusText`，但前端提交和后端判断只使用英文枚举。

建议提供统一字典接口：

```text
GET /api/dictionaries
GET /api/dictionaries/{dictCode}
```

字典来源分为三类：

- 固定枚举：角色、载体状态、保管期限、密级、开放状态、各类业务状态。
- 初始化字典表：档案门类、标签。
- 系统配置：上传白名单、AI 批大小、征集数量限制等。

清单状态的中文展示必须结合 `source_type` 映射，不能只按 `status` 全局翻译，例如 `rejected` 在移交侧展示“已回退”，在征集侧展示“已拒绝”。

### 3.1.5 上传、下载和导出

上传接口只供前台接收、业务附件和销毁现场照片等受控场景使用。所有上传都必须经过格式、大小、MIME、SHA-256 和 ClamAV 检查，只有扫描通过后才创建文件记录并写入 MinIO。移交单位和公众编制清单时的拖拽文件只在浏览器本地解析文件名，不调用上传接口。

上传成功返回：

```json
{
  "fileId": 1,
  "businessType": "staging_file",
  "originalFilename": "example.pdf",
  "fileSize": 1024,
  "sha256": "64位哈希",
  "scanResult": "safe",
  "matchStatus": "matched"
}
```

下载和预览接口必须先复用档案查询鉴权，通过后才生成 MinIO 预签名 URL 或返回文件流，并写入 `archive_access_logs`。导出 PDF、Excel 的接口按业务生成文件流；如业务要求留存，则同时写入 `business_attachments`。

### 3.1.6 业务状态并发

所有状态流转接口必须在 Service 层重新读取当前状态并校验，不信任前端传入的旧状态。确认入库、上架、出库、归还、审批、销毁等接口必须在事务内处理，并按数据库设计文档的并发口径锁定关键记录。

## 5. 安全设计

### 5.1 认证与授权

系统使用 Sa-Token 实现登录认证、角色校验和权限校验。

认证流程：

1. 用户提交账号密码或验证码。
2. 后端校验身份并签发 token。
3. 前端后续请求携带 token。
4. 后端拦截器校验 token 有效性。
5. 业务接口根据 AuthContext 校验角色、权限、密级和数据范围。

### 5.2 密级与开放控制

档案访问必须同时考虑密级、开放状态和数据范围。

- 公众用户只能访问 `非密` 且 `公开` 的档案。
- 内部查阅者按所属单位、全宗范围和密级上限访问。
- 移交单位经办人只能访问本单位清单和移交状态，不能进入正式档案管理后台。
- 馆领导只能处理授权范围内的审批事项。
- 文件预览和下载必须复用档案查询鉴权，通过后才生成 MinIO 预签名 URL。

### 5.3 操作日志

以下操作必须记录日志：

- 登录、登出
- 新增、修改、删除元数据
- 清单提交、接收、回退、入库、上架
- 文件上传、暂存转正式、删除
- 密级调整、开放调整、审批
- 借阅申请、审批、出库、归还
- 鉴定、销毁清册生成、销毁审批、确认销毁

日志字段至少包含：操作人、操作时间、操作类型、操作对象、操作详情、IP 地址。

## 6. AI 服务对接

### 6.1 AI 调用链路

```text
用户点击 AI 功能
    ↓
前端请求后端 AI 接口
    ↓
后端组装最小必要上下文
    ↓
调用 AI API
    ↓
提取 <JSON> 内容
    ↓
格式校验和白名单过滤
    ↓
返回前端展示
    ↓
用户确认后走正式业务接口
```

本期 AI 只落在 4 个入口：

- 内部检索：自然语言转内部检索表单 JSON。
- 公众检索：自然语言转公开检索表单 JSON。
- 接收清单补全：默认每 50 条清单条目拆成一个 AI 批次。
- 档案研判：默认每 50 条正式档案元数据拆成一个 AI 批次。

### 6.2 对接方式

- API 协议：OpenAI 兼容 HTTP JSON 接口
- API Key：通过环境变量配置，不写入代码仓库
- 超时：连接超时 5 秒，读取超时 15 秒
- 检索重试：JSON 校验失败时最多重新调用 3 次
- 批处理重试：不自动重试成功批次；任务部分完成时由管理员点击重试失败批次
- 降级：AI 不可用时隐藏或禁用 AI 功能，保留手工流程

### 6.3 AI 使用边界

- AI 只处理元数据和自然语言条件。
- AI 不读取 MinIO 文件正文。
- AI 不生成档号。
- AI 不覆盖密级、保管期限、是否公开。
- AI 不直接执行数据库或文件操作。
- 检索提示词只注入固定分类和当前用户可见标签集合，不注入档案题名。

## 7. 文件上传与入库

### 7.1 移交单位侧文件拖拽

移交单位或公众在编制清单时，可以拖拽电子文件到页面中，但该操作只在浏览器本地解析文件名、扩展名和大小提示，不上传文件本体。

目的：

- 降低移交单位账号泄露后的文件上传风险。
- 避免未验收文件进入档案馆对象存储。
- 保持“线上清单 + 线下交接”的业务口径。

### 7.2 前台接收阶段上传

前台管理员接收 U 盘或现场电子文件时，统一在清单页面上传。

流程：

1. 前台选择或拖拽 U 盘中的电子文件。
2. 后端校验登录和接收权限。
3. 系统按清单条目中的档案文件名匹配。
4. 后端校验文件类型、大小并计算 SHA-256。
5. 后端调用 ClamAV 扫描文件流或临时文件。
6. 扫描通过后文件进入 MinIO 临时暂存路径。
7. 系统记录上传人、上传时间、原文件名、哈希、格式、大小、扫描结果、扫描说明和匹配状态。

### 7.3 临时路径与正式路径

接收阶段还没有正式档号，因此电子文件先进入暂存路径。

```text
archive-files/_staging/{sourceType}/{batchId}/{stagingFileId}/{fileName}
```

其中 `{stagingFileId}` 使用 `staging_files.id`，而不是拖拽批次号；同一次拖拽上传的多个文件可以共享 `upload_batch_no`，但每个暂存对象路径必须依靠 `batchId + staging_files.id` 保证唯一。未匹配文件允许没有清单条目 ID，因此路径不使用 `itemId`。

管理员确认入库并生成正式档案后，后端将文件复制到正式路径。

```text
archive-files/{archiveNo}/{fileId}/{fileName}
```

其中 `{fileId}` 使用 `archive_files.id`。实现时先创建 `archive_files` 记录，初始 `file_status = pending`，再按正式路径复制 MinIO 对象；复制成功后更新 `file_status = normal`、回写 `staging_files.archived_file_id` 并清理暂存对象。若复制失败，保留 `archive_files` 记录并标记 `file_status = failed`，后台可重试暂存转正式。

### 7.4 文件异常

以下情况进入异常状态，由前台管理员确认或回退：

- 文件打不开
- 文件格式不允许
- 文件大小超过限制
- 清单有文件名但 U 盘缺失
- U 盘有文件但清单没有对应项
- 同名文件重复
- 哈希重复但来源不一致

## 8. 性能与扩展

### 8.1 性能策略

- PostgreSQL 建立常用筛选字段索引，如档号、题名、年度、分类、密级、开放状态、来源单位。
- 对题名、责任者、文件名等文本字段启用 `pg_trgm` 扩展并建立 GIN/GiST 索引，支撑模糊查询和包含查询。
- 大批量列表查询使用稳定排序字段和游标式分页；普通管理列表可继续使用 MyBatis-Plus 分页。
- 文件上传本期采用后端转发到 MinIO，便于统一鉴权、哈希计算和审计。
- 文件入库前同时记录 SHA-256、MIME 类型、扩展名、大小和病毒扫描状态。
- 大文件或高并发上传场景后续可扩展为预签名 URL 直传。
- Nginx 托管前端静态资源，减少后端压力。
- Spring Boot Actuator 只暴露健康检查等必要端点，详细指标放在内网或管理侧访问。

### 8.2 可能扩展方向

- 引入 Redis 缓存热点字典、权限和统计数据。
- 引入 Elasticsearch 做全文检索，但不作为本期范围。
- 档案规模增长后按全宗或年度分区。
- 引入后台任务处理批量四性检查和大批量数据研判；本期优先使用 Spring TaskScheduler，不单独引入 XXL-JOB。
- 扩展库房结构为库房、区、列、节、层、盒位。
