# 原型交互设计规范

---

## 1 基本布局约定

所有后台管理类页面采用统一的布局框架：

```
┌──────────────────────────────────────────────────┐
│  顶部栏              │
├────────────┬─────────────────────────────────────┤
│            │                                     │
│  左侧导航栏  │           内容区                    │
│            │                                     │
│            │                                     │
└────────────┴─────────────────────────────────────┘
```

**左侧导航栏**
**内容区**
**公众类页面**

- 公众门户不使用后台管理框架，采用独立的顶部导航布局（顶部导航 + 内容区）

## 2 交互设计调研要求

在设计每个页面原型前，需完成以下两项调研并记录到该页面的原型设计文档中。

### 2.1 业务场景归属分析

- 明确该页面属于哪一个业务场景（以业务场景文档：[new-doc/业务场景.md](../new-doc/业务场景.md) 为准）
- 参照数据库设计文档：[new-doc/数据库设计.md](../new-doc/数据库设计.md)，确认页面涉及的数据实体、字段约束、状态枚举和表间关系
- 参照新版 PlantUML 图目录：[new-doc/puml/](../new-doc/puml/)，确认页面所在门户、业务流程、数据流和状态流转口径
- 说明该页面与上下游业务场景之间的关系（上游输入、下游消费、并列关系）
- 标注该页面涉及的状态流转节点

### 2.2 用户操作分析

- 列出该页面所有使用角色
- 针对每个角色，列出其在该页面上可执行的全部操作
- 区分主路径操作与异常路径操作
- 标注操作的结果（触发状态变更 / 查询 / 跳转 / 导出等）

## 3 启发式评估标准

原型设计完成后，须使用以下 Nielsen 十大可用性启发式原则进行自查，发现的问题在原型设计验收文档中逐项记录。

### 3.1 系统状态可见性（Visibility of System Status）

系统应在合理时间内通过适当反馈，始终让用户了解当前发生的事情。

- 操作后应有即时反馈（加载状态、进度条、操作成功/失败提示）
- 涉及后台处理的流程应展示处理进度或状态标记

### 3.2 系统与现实世界的匹配（Match Between System and the Real World）

设计应使用用户熟悉的语言和概念，而非系统术语，并遵循现实世界惯例。

- 使用档案行业通用术语（如"全宗""案卷"），不使用内部技术代号
- 图标含义应直观，不依赖文字说明

### 3.3 用户控制与自由（User Control and Freedom）

用户会误操作，需要清晰的"紧急出口"来离开非预期状态，支持撤销/重做。

- 表单填写支持取消并返回
- 批量操作前应有确认步骤
- 关键操作支持撤销（如误删恢复）

### 3.4 一致性与标准（Consistency and Standards）

用户不应疑惑不同场景下的相同词语、情境或操作是否含义一致，应遵循平台与行业惯例。

- 同一操作在不同页面的行为与视觉表现保持一致
- 按钮样式、颜色语义全系统统一
- 导航结构与操作入口保持一致

### 3.5 错误预防（Error Prevention）

优于优秀错误提示的设计，是根本预防错误发生。应消除容易出错的条件，或在提交前进行检查与确认。

- 关键字段输入格式提示与校验
- 危险操作（删除、销毁）设置二次确认
- 不可逆操作前明确告知后果

### 3.6 识别而非记忆（Recognition Rather Than Recall）

通过让操作、对象、选项可见，尽量减少用户的记忆负担。

- 常用操作置于易达位置
- 已填写或已选内容在提交前可预览
- 使用面包屑帮助用户了解当前位置

### 3.7 使用的灵活性与效率（Flexibility and Efficiency of Use）

为新手不可见的快捷方式可以加速专家用户的操作，允许用户自定义常用操作。

- 列表页支持批量操作
- 提供常用筛选条件的快捷入口
- 表单支持键盘 Tab 切换

### 3.8 美观与简约设计（Aesthetic and Minimalist Design）

对话框不应包含无关或极少使用的信息，每一额外单元都在与真正重要的信息竞争。

- 内容区只展示当前任务所需信息
- 不在主要操作区域放置次要信息
- 使用分组与留白区分信息层级

### 3.9 帮助用户识别、诊断并修复错误（Help Users Recognize, Diagnose, and Recover from Errors）

错误提示应使用清晰的语言（不使用代码），准确指出问题，并建设性地提出解决方案。

- 错误提示说明具体原因（如"身份证号格式不正确"），而非"输入错误"
- 表单校验失败时高亮错误字段并附提示
- 提供修正建议或自动修正选项

### 3.10 帮助与文档（Help and Documentation）

即使系统无需文档即可使用，也应提供易于搜索、聚焦于用户任务的帮助，列出具体步骤且不过于冗长。

- 复杂操作流程提供步骤引导或操作提示
- 关键字段旁提供帮助图标与说明
- 提供可搜索的操作手册或常见问题入口

## 4 每个页面需生成的文件

设计每个页面原型时，须按以下**绝对顺序**依次生成三个文件，放置在该页面路径对应的目录下。上一文件完成后才能开始下一文件，不得并行或颠倒顺序。

**生成顺序：**

```
原型设计文档(.md) → 原型HTML(.html) → 验收文档(.md)
```

原因：
- 设计文档是 HTML 的唯一依据，必须先完成设计再动手写页面
- 验收文档须在 HTML 完成后对照实际产物编写，不可在设计阶段预设通过结论

### 4.1 原型设计文档（`.md`）**【第一步】**

文件名格式：`{页面名称}-原型设计.md`

内容结构：
1. **页面概述**：页面名称、所属门户、页面路径
2. **业务场景归属分析**：所属业务场景、与其他场景的关系、涉及的状态节点（对应第 2.1 节要求）
3. **用户与操作分析**：角色列表、各角色操作、主/异常路径区分（对应第 2.2 节要求）
4. **页面布局说明**：布局结构、关键区域划分
5. **交互逻辑说明**：操作流程、状态流转、联动行为
6. **启发式自查记录**：按第 3 节十大原则逐项填写自查结论

### 4.2 原型 HTML 文件（`.html`）**【第二步，须在 4.1 设计文档完成后进行】**

文件路径与页面清单中定义的路径一致，使用静态 HTML + 内联 CSS 实现可交互原型。

要求：
- 反映页面实际布局与交互逻辑
- 核心操作流程可通过点击模拟完整路径
- 样式符合本规范定义的布局约定

**样式组织规则：**

- 优先引用 `common/css/` 下的公共样式（`base.css`、`components.css`、`shell.css`），公共样式已覆盖的规则不得在页面 HTML 中重复定义
- 公共样式未覆盖的页面专属样式，写在该页面 HTML 的 `<style>` 中
- 目的：控制单个 HTML 文件长度，便于后续调整与维护
- **不得为了缩短文件长度而精简交互或降低原型保真度**——交互完整性优先于文件体积

### 4.3 原型设计验收文档（`.md`）**【第三步，须在 4.2 HTML 完成后进行】**

文件名格式：`{页面名称}-验收.md`

内容结构：
1. **验收范围**：本次验收对应的页面与版本
2. **功能验收项**：逐条列出需验证的功能点，每项包含验收标准与通过/未通过状态
3. **交互验收项**：针对操作响应、状态变更、错误提示、跳转逻辑等交互细节的验收
4. **启发式评估验收**：按十大可用性启发式原则逐项评估，记录是否符合及具体问题
5. **问题记录**：发现问题的编号、描述、严重程度、建议修复方案
6. **验收结论**：总体通过/不通过，附遗留问题清单

## 5 工作流程

```
读取业务场景文档 + 页面清单
        │
        ▼
  对每个页面执行：
        │
        ├─ 1. 业务场景归属分析
        ├─ 2. 用户操作分析
        ├─ 3. 页面布局与交互设计
        └─ 4. 按 ## 4 绝对顺序输出三个文件：
             ├─ (1) 原型设计文档（.md）———— 必须先完成
             ├─ (2) 原型 HTML 文件（.html）—— 以设计文档为依据
             └─ (3) 验收文档（.md）———— HTML 完成后对照实际产物编写
```

三个文件的生成必须严格按 ## 4 定义的顺序执行：先设计、再实现、后验收。不得并行生成或颠倒顺序。
