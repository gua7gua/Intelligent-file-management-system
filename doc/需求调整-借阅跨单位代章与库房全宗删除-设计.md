# 需求调整：借阅跨单位代章 + 库房/全宗删除

> 日期：2026-06-20　　分支：feat/integration-fang
> 状态：设计已与项目经理确认，待实施

## 1. 背景与目标

联调阶段发现三处业务缺口，本次一并补齐：

1. **内部人员借阅跨单位纸质档案**：原设计「内部人员借阅本单位纸质档案 → 打印凭证回原单位盖章」，遗漏了「借阅**其他单位**纸质档案」的场景。借阅人非该档案原属单位人员，无法回原单位盖章。改口径：**跨单位纸质借阅由档案馆代原单位盖章**。
2. **库房无法删除**：误建/改用途的库房无法清理。新增库房删除，校验「无活动档案盒」。
3. **全宗无法删除**：误建全宗无法清理。新增全宗删除，关联档案的 `fonds_id` 置空（字段本就非必填）。

## 2. 现状（已核实）

### 2.1 借阅流程
- 借阅申请/出库环节**本身不做**单位归属与密级校验，全靠检索层 `SearchService.internalSearch` → `buildInternalWrapper` 用 `dataScope` + `maxSecurityLevel` 兜底（`SearchService.java:91-135`）。
- 当前检索是**单一 dataScope + 单一密级上限**，**未实现**「本单位按密级上限 + 其他单位仅非密」混合规则（`DataScope.java` 仅 own_org/own_fonds/all）。
- 跨单位纸质借阅在借阅代码中**零分支**，`doc/业务场景.md:90` 明确「不做复杂跨馆借阅或物流流程」。
- 凭证 PDF（`PdfGenerator.java:202-210`）有两块盖章留白：「单位意见（盖章）」「档案馆归还确认（盖章）」，均为静态文案，系统不验章、不存章。
- 凭证号是出库唯一电子凭据（`BorrowService.java:249-251`）。
- 借阅状态机：applied→approved/rejected→voucher_issued→checked_out→returned/abnormal_return（`BorrowStatus.java:13-21`）。

### 2.2 库房管理
- 库房仅 C/R/U，无 D（`WarehouseController.java` 无 `@DeleteMapping`）。实体已预留 `deleted_at` 但无代码写入。
- 依赖链：`warehouse_rooms` → `storage_locations`(架位，建库房时批量生成) → `archive_boxes`(档案盒) → `archive_box_items` → `archive`。
- 占用统计可复用 `WarehouseService.java:64-67`（COUNT_OCCUPIED_BY_ROOM_SQL，按库房统计 status IN ('normal','full') 的活动盒）。

### 2.3 全宗管理
- 全宗仅 C/R/U，无 D；有关联时更新退化为只改 status（`FondsService.java:103-136`）。
- 前端注释明确「§17.4 全宗不做物理删除，统一停用」（`fonds/index.vue:288`）——**本次推翻此口径**。
- `archives.fonds_id`、`archive_boxes.fonds_id` 均 nullable；外键 `fk_archives_fonds_id`/`fk_archive_boxes_fonds_id` 无 ON DELETE（默认 RESTRICT，`V12__add-foreign-keys.sql:10,23`）。
- 关联统计可复用 `FondsService.countAssoc`（`FondsService.java:164-168`）。

## 3. 需求 1：借阅跨单位纸质档案（检索分级 + 档案馆代章）

### 3.1 检索分级（`SearchService`）

将 `own_org` 内部查阅者的检索条件由：
```
organization_id = 本单位 AND security_level <= maxSecurityLevel
```
改为混合规则：
```
(organization_id = 本单位 AND security_level <= maxSecurityLevel)
OR
(organization_id <> 本单位 AND security_level = 'NONE')
```

**适用范围（精确）**：
- **仅对内部查阅者生效**（角色 `internal_reader`，对应 `dataScope = own_org`）。
- 馆领导、系统管理员、前台档案管理员、后台档案管理员（`dataScope = all` 或管理角色）**不受限**，保持全量 `<= maxSecurityLevel`。
- `own_fonds`（本全宗）保持现状。
- 公众端（仅公开）、移交人员（仅本单位移交清单）走各自独立检索路径，**不涉及**。

**实现要点**：
- 改造 `SearchService.buildInternalWrapper` / `applyDataScope`，用 QueryWrapper 嵌套构造 OR 分支：
  `wrapper.and(w -> w.and(o -> o.eq("organization_id", userOrgId).le("security_level", maxSL))
                       .or(o -> o.ne("organization_id", userOrgId).eq("security_level", SecurityLevel.NONE)))`
- 触发条件以 `dataScope == own_org` 判定（实现时核实 `internal_reader` 角色 ↔ `own_org` 的映射，确保不误伤管理角色）。
- 同步检查档案**详情**查询的权限路径，确保与列表一致（列表可见则详情可开），避免「列表能看到、点进详情 403」。

### 3.2 凭证盖章口径（`PdfGenerator` + `BorrowService.exportVoucher`）

`exportVoucher`（`BorrowService.java:203-231`）生成 PDF 时，比较：
- 借阅人 `organization_id`（来自 `AuthContext` / `User`）
- 档案 `organization_id`（`Archive.organization_id`）

分支：
- **相同**（本单位借阅）：凭证「单位意见（盖章）」文案**不变**。
- **不同**（跨单位借阅）：文案改为 **「档案馆代原属单位（{档案原属单位名}）意见（档案馆盖章）」**；归还确认区不变。

**实现要点**：
- `PdfGenerator.generateBorrowVoucherPdf`（`PdfGenerator.java:130-222`）签名增 `boolean crossOrg` 与 `String archiveOrgName`（原属单位名）两个参数。
- `exportVoucher` 查出档案原属单位名，比较后传入；本单位借阅 `crossOrg=false`，文案区维持原文。
- 原属单位名通过档案 `organization_id` 查 `organizations` 表获得（`BorrowService` 已注入 `OrganizationMapper`）。

## 4. 需求 2：库房物理删除

### 4.1 后端
- `WarehouseController` 增 `@DeleteMapping("/rooms/{roomId}")`，权限 admin。
- `WarehouseService.deleteRoom(Long roomId)`：
  1. 查库房存在（`organizationId`/`roomNo` 等用于审计）。
  2. **校验无活动档案盒**：该库房所有 `storage_locations` 下，`archive_boxes` 中 `status IN ('normal','full')` 的记录数 = 0（复用 `COUNT_OCCUPIED_BY_ROOM_SQL`）。有 → 抛 `BUSINESS_CONFLICT`(409)「该库房存在档案盒，无法删除，请先移出档案盒」。
  3. 无活动盒：把残留历史盒（moved/destroyed）的 `location_id` 置 NULL → 物理删该库房全部 `storage_locations` → 物理删 `warehouse_rooms`。
  4. 审计日志 `auditService.log(...)`。

**口径说明**：用「无**活动**盒」而非「0 条盒记录」。否则只要库房曾放过盒（即便已搬走/销毁）就永远删不掉。历史盒 `location_id` 置空以保留盒记录、解除架位外键。

### 4.2 前端
- `warehouse.ts` 增 `deleteWarehouseRoom(roomId)`。
- `RoomList.vue` 库房项增「删除」操作（图标按钮 + `ElMessageBox.confirm` 二次确认）；catch 中 `ElMessage.error` 回显 409 文案。

## 5. 需求 3：全宗物理删除

### 5.1 后端
- `FondsController` 增 `@DeleteMapping("/{fondsId}")`，权限 admin。
- `FondsService.deleteFonds(Long fondsId)`：
  1. 查全宗存在。
  2. 统计关联（复用 `countAssoc`）——用于前端提示，**不阻止删除**。
  3. **先**置空关联（外键 RESTRICT，必须先解除）：
   - `UPDATE archives SET fonds_id = NULL WHERE fonds_id = ?`
   - `UPDATE archive_boxes SET fonds_id = NULL WHERE fonds_id = ?`
  4. `DELETE FROM fonds WHERE id = ?`（物理硬删）。
  5. 审计日志。

> `archive_boxes.fonds_id` 因外键约束必须与 `archives` **一并置空**，否则物理删除被数据库阻断。此为硬约束，不可选。

### 5.2 前端
- `fonds/index.vue`「停用」旁增「删除」按钮；删除 `fonds/index.vue:288` 处「不做物理删除」注释并改为支持删除。
- 删除前按 `archiveCount`/`boxCount` 弹确认框，明示「该全宗关联 N 条档案/档案盒，删除后其全宗字段将被清空」。
- 接入已存在的 `removeFonds`（`api/fonds.ts:31-37`，原残留占位，本次接真实端点）。

## 6. 共同约定

- **权限**：库房/全宗删除限 admin（馆领导/系统管理员），与现有管理类操作一致。
- **DB 迁移**：三需求均**不改表结构**（`deleted_at`/`fonds_id`/`location_id` 等字段已就绪），无需新 migration。
- **删除方式**：库房、全宗均为**物理硬删**（用户指定），与 Organization 软删风格不同，需在前端确认框强调不可恢复。
- **审计**：两个删除操作均写 `auditService.log`，沿用现有模块码风格。
- **错误码**：库房有活动盒用 `BUSINESS_CONFLICT`(409)；全宗删除不阻止（前端提示后直接执行）。

## 7. 测试与验证计划

- **需求 1（高风险，必须全量回归）**：
  - 检索分级：构造 own_org 用户，验证可见「本单位≤密级上限 + 其他单位非密」，不可见其他单位秘密/机密；验证 all 角色不受影响。
  - 凭证代章：构造跨单位纸质借阅，导出凭证 PDF，核对盖章区文案含原属单位名与「档案馆代章」字样；本单位借阅凭证文案不变。
  - **重跑 e2e（90 用例）与 7 角色测试**，关注内部查阅者相关用例的检索断言是否需要调整。
- **需求 2**：无盒库房可删（架位/库房物理消失）；有活动盒库房删除返回 409；含历史盒的库房删除后历史盒 `location_id` 为空、盒记录仍在。
- **需求 3**：无关联全宗直接删；有关联全宗删除后 `archives`/`archive_boxes` 的 `fonds_id` 为 NULL、全宗记录消失；验证前端确认框文案。
- 验证手段：后端单测/接口测试 + 前端浏览器实测（自主截图工具链）。

## 8. 风险与影响面

| 风险 | 等级 | 应对 |
|------|------|------|
| 检索分级改动影响内部查阅者所有检索行为，牵动 e2e/角色测试 | 高 | 全量回归，必要时调整测试数据/断言 |
| 检索分级误伤管理角色（馆领导等） | 中 | 触发条件严格限定 `dataScope=own_org`，实现时核实角色映射，测试覆盖 all 角色 |
| 列表与详情权限不一致导致「可见但 403」 | 中 | 同步检查详情查询路径 |
| 物理硬删不可恢复 | 中 | 前端强提示 + 二次确认 |
| 凭证 PDF 文案/版式回归 | 低 | 对比本单位/跨单位两张凭证 |
