# AI / 短信 手动复测用例（DeepSeek / 阿里云短信启用场景）

> 自动化 e2e 套件所对的基线容器未配置 `DEEPSEEK_API_KEY` / 阿里云短信密钥，AI 与短信链路无法在自动化套件中覆盖。
> 本文档给出 **AI 启用 + 短信启用** 运行态下的手动复测用例，使用 chrome-devtools（或浏览器人工）逐条执行。
> AI 部分已由 chrome-devtools MCP 实测通过（见各用例「实测结果」）；短信部分需手机接收验证码，留人工执行。

---

## 0. 前置：启用 AI / 短信的运行态

### 0.1 环境变量

| 变量 | 用途 | 来源 |
|------|------|------|
| `DEEPSEEK_API_KEY` | DeepSeek 大模型（AI 补全/研判/检索/编研） | DeepSeek 开放平台 |
| `ALIYUN_SMS_ACCESS_KEY` / `ALIYUN_SMS_SECRET` | 阿里云短信（注册/找回密码验证码） | 阿里云 RAM |
| `ALIYUN_SMS_ENABLED=true` | 打开真实短信发送（默认 false 走 fallback 固定码 123456） | 启动时注入 |

后端配置（`backend/src/main/resources/application.yml`）：
- AI 开关由 DB 配置 `ai.enabled`（V15 种子为 `true`）控制；只要 `DEEPSEEK_API_KEY` 存在即真实调用。
- 短信开关 `aliyun.sms-auth.enabled=${ALIYUN_SMS_ENABLED:false}`；关闭时 `FallbackSmsCodeService` 用固定码 `123456` 并在日志打印 `[SMS-FALLBACK] phone=... 固定验证码=123456`。

### 0.2 启动命令（dev）

```bash
# 后端：AI 走 shell 已有的 DEEPSEEK_API_KEY；短信按需开启
cd backend
ALIYUN_SMS_ENABLED=true ./mvnw spring-boot:run -Dspring-boot.run.profiles=dev   # 8080

# 前端
cd frontend && npm run dev   # 3000，/api 代理到 8080
```

### 0.3 连通性自检

```bash
# DeepSeek 可达性（应回 OK 类短文本）
curl -s https://api.deepseek.com/chat/completions \
  -H "Authorization: Bearer $DEEPSEEK_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"deepseek-chat","messages":[{"role":"user","content":"只回OK"}],"max_tokens":5}'
```

> AI 调用偶发瞬时降级（外部服务波动），重试即可。中性检索词（「会议纪要」「老城改造」）稳定命中；含敏感倾向的词（「会计凭证」）AI 会主动加「非密+公开」约束，基线会计档案多为内部/不公开，命中 0 条属预期。

## 1. AI 整批补全（W-A 捐赠入库 / W-B 移交入库）

**能力**：根据待入库条目的电子件文件名（+已有元数据），调用 DeepSeek 推断题名、形成日期、分类、责任者、标签，回填到「待入库与上架」表单供人工核对确认。

**角色**：`liu.back`（档案管理员·后台）。

**步骤**：
1. `/admin/pending-archive`，点开一个「已接收未入库」批次卡（含电子件）。
2. 点顶部「**AI 整批补全**」（真实调用 DeepSeek，约 1–5 秒/批）。
3. 顶部状态由「AI：失败/未跑」→「**AI：已完成**」；条目元数据被 AI 回填。
4. （描述性文件名才有丰富回填，如 `05-old-city-photo-2003.png` → 题名「老城区旧貌照片（2003年）」、形成日期 `2003-01-01`、分类「音像档案」、标签「照片,城市风貌,2003年」。泛化文件名如 `测试移交档案` 推断有限。）
5. 选档案盒（按分类过滤）、点「确认入库」→ 产出正式档号 ARC-xxxxxx（状态 `pending_shelf`）。

**实测结果（2026-06-23，chrome-devtools）**：
- BAT-000020「AI：失败」→ 点 AI 整批补全 → 后端 `POST /admin/pending-archive/batches/20/ai-completion` 200，`ai-tasks/15` 返回 `status=completed, successBatches=1, failedBatches=0`（耗时 ~1s）→ 页面状态变「**AI：已完成**」。✅
- 另独立复测 BAT-000019（原「AI：失败」）→ 点「AI 整批补全」→ 头部状态由「AI 补全：失败」变「**AI 补全：已完成**」、批次标记变「AI：已完成」。✅（证明失败批次可由 AI 补全恢复）
- 结论：AI 补全在 DeepSeek 启用时正常；基线容器失败仅因未配 `DEEPSEEK_API_KEY`。

## 2. AI 数据研判（W-G）

**能力**：扫描正式档案元数据，AI 生成「缺失字段 / 标签建议 / 标签错配 / 分类冲突」等候选建议，逐条采纳/不采纳/删除。

**角色**：`liu.back`。

**步骤**：
1. `/admin/data-analysis`，默认范围 5 门类全选、年度 2010–2026、任务类型「综合」、勾「**包含 AI 候选建议**」。
2. 点「S 开始扫描」→ 生成任务 `ANA-YYYYMM-NNNN`。
3. 任务完成后「异常建议列表」出现候选（含 AI 生成的标签建议与冲突判定）。
4. 点异常项 → 右侧「条目详情」→「采纳」（移入「已采纳」，进入档案管理待处理）。

**实测结果（2026-06-23，chrome-devtools）**：
- 任务 `ANA-202606-0005`，扫描 40 档案，**产出 43 条候选建议**，其中：
  - **标签建议**（AI 据题名生成）：如 ARC-000024「2023 年度道路改造工程设计文件」→「科技档案、工程设计、道路改造」；ARC-000033「干部任免审批材料」→「人事档案、干部任免、审批材料」。
  - **标签错配**（AI 智能冲突检测）：ARC-000005「标签『影像资料』和『社会捐赠』与会计档案门类明显冲突」。
- 点「采纳」ARC-000039（缺失字段 responsible）→ 项移入「已采纳」。✅

## 3. AI 智能检索（W-H，内部 / 公众两端）

**能力边界**：本系统 AI 检索是「**自然语言 → 结构化检索条件生成**」（输出关键词/分类/年度/密级/开放状态等并映射回检索表单），**不是向量语义检索、也不是多轮对话问答**。

### 3.1 内部 AI 检索（小李）

**角色**：`li.reader`（内部查阅者）。**页**：`/internal/search`。

**步骤**：
1. 展开顶部「AI 检索条件生成」面板。
2. 输入 `会议纪要` → 点「生成查询条件」（真实调用 AI，约 2–5 秒）。
3. 系统返回结构化条件（如 `{"keywords":["会议纪要"]}`）。
4. 点「应用条件并检索」→ 条件映射回表单并执行检索。

**实测结果（2026-06-23，chrome-devtools）**：
- 输入「会议纪要」→ AI 返回 `{"keywords":["会议纪要"],"tags":[]}` → 应用检索 → **命中 2 条**：ARC-000018「2022 年度档案工作会议纪要」、ARC-000022「2022 年度工程建设会议纪要」。✅

### 3.2 公众 AI 检索（小周）

**角色**：`zhou.public`（社会公众）。**页**：`/public/search`。

**步骤**：「AI 智能查询」卡片输入 `查找老城改造的档案` →「生成查询条件」→「应用条件并检索」。
**预期**：命中若干条城建/文书类公开档案（ARC-000016~023 范围）。

## 5. 短信验证码（人工执行，已通过）

> 启用 `ALIYUN_SMS_ENABLED=true` 的 dev 后端（8080），用真实手机号人工执行；**2026-06-23 实测通过**（发码 `code=OK`，见各用例实测结果）。

### 5.0 位数校验核查结论（4 位 vs 6 位，重要）

真实阿里云短信验证码为 **4 位数字**（`AliyunSmsCodeService` 调 `sendSmsVerifyCode`，由阿里云生成并下发），而 fallback 固定码为 6 位（`123456`）。已核查全链路 **无 4/6 位数硬编码阻断**，真实 4 位码可正常提交校验：

| 层 | 注册 (`/public/register`) | 找回密码 (`/public/forgot-password`) | 结论 |
|---|---|---|---|
| 前端 input | `inputmode="numeric" required`，**无 `maxlength`/`pattern`**（`register/index.vue:33`） | 同（`forgot-password/index.vue:38`） | 接受任意位数 |
| 前端 JS | 无 `smsCode.length` 校验（仅 `errors.length`） | 同 | 4 位可提交 |
| 后端 DTO | `PublicRegisterRequest.smsCode` 仅 `@NotBlank` | `ResetPasswordRequest.smsCode` 仅 `@NotBlank` | 无位数约束 |
| 发码/校验 | `AliyunSmsCodeService`：阿里云生成（默认 4 位）+ `CheckSmsVerifyCode` 校验 | 同 | 阿里云托管，位数随其生成 |

→ **真实 4 位短信码全链路可通过**；`123456` 仅是 SMS 关闭时 `FallbackSmsCodeService` 的固定值，不影响真实短信。

> 实测结论（2026-06-23）：真实凭据下 `sendSmsVerifyCode` 返回 `code=OK`（发码成功）、`CheckSmsVerifyCode` 校验通过（注册/重置均成功）——源码注释所述「verifyResult 防御性解析」在真实场景下工作正常。

### 5.1 公众注册（短信验证码）

**页**：`/public/register`。**手机号**：`18877600249`（测试号）。

**步骤**：
1. 填登录名、密码、手机号 `18877600249`、勾协议。
2. 点「获取验证码」→ 手机收到 **4 位**短信码（或 fallback 日志的 `123456`）。
3. 填入验证码（4 位）→ 提交注册 → 注册成功，可用新账号登录公众门户。
**预期**：`users` 新增 `public_user`，状态 `active`；阿里云控制台可见发送记录。

**实测结果（2026-06-23）**：✅ 通过——带 SMS 的 dev 后端日志 `[SMS-ALIYUN] 发码响应 phone=18877600249 code=OK message=OK`，手机收到 4 位验证码，填入完成注册。

### 5.2 忘记密码（短信验证码）

**页**：`/public/forgot-password`。

**步骤**：
1. 填手机号 `18877600249` →「获取验证码」→ 手机收到 **4 位**短信码（或 fallback `123456`）。
2. 填验证码（4 位）+ 新密码 → 提交 → 密码重置成功，可用新密码登录。
**预期**：对应用户密码哈希更新；短信发送记录可见。

**实测结果（2026-06-23）**：✅ 通过——忘记密码发码日志 `[SMS-ALIYUN] phone=18877600249 code=OK`，手机收到 4 位码，`CheckSmsVerifyCode` 校验通过、密码重置成功。
