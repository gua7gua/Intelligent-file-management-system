# 数据库设计

> 本文档基于 `new-doc/业务场景.md` 设计数据库结构。目标是覆盖移交、征集、入库、检索、借阅、审批、鉴定、销毁、库房、盘点、编研、统计研判、保存和系统管理等场景，同时避免过度设计。

---

## 1. 设计边界

### 1.1 技术口径

| 项目 | 方案 |
|------|------|
| 数据库 | PostgreSQL 17 推荐，最低 PostgreSQL 16 |
| ORM | MyBatis-Plus |
| 迁移管理 | Flyway |
| 文件本体 | MinIO 对象存储 |
| 文件记录 | 数据库只保存对象路径、哈希、大小、格式、状态和业务关联 |
| 检索增强 | `pg_trgm` + GIN 索引，先做元数据模糊检索 |

### 1.2 本期不做的复杂设计

| 不做 | 原因 |
|------|------|
| 不引入流程引擎 | 本期只有馆领导单节点审批，用 `approval_requests` 足够 |
| 不拆复杂库房结构 | 按“库房房间-机架-层-盒位”生成架位，满足当前物理模型 |
| 不做清单多版本协同编辑 | 清单提交后只读；回退条目下次新建清单补交 |
| 不做独立 BI 统计库 | 统计从正式业务表实时查询或简单定时汇总 |
| 不做 RAG、向量库、正文检索 | AI 只看元数据，不读取 MinIO 正文 |
| 不做越级查阅授权表 | 内部查阅严格按密级上限和单位/全宗范围过滤 |

### 1.3 通用字段约定

除关系表外，业务表默认包含以下字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGSERIAL | 主键 |
| `created_at` | TIMESTAMPTZ | 创建时间 |
| `updated_at` | TIMESTAMPTZ | 更新时间 |
| `created_by` | BIGINT | 创建人，可空；系统任务可为空 |
| `updated_by` | BIGINT | 更新人，可空 |
| `deleted_at` | TIMESTAMPTZ | 仅少量可软删表使用；档案、审批、日志不软删 |

命名约定：

- 表名和字段名统一使用 `snake_case`。
- 枚举值统一使用小写英文，前端展示中文。
- 金额、数量、状态等不要存中文；中文只作为字典展示。
- JSON 字段只用于快照、AI 建议、规则结果等弱结构数据，不承载主查询字段。
- 首轮脚手架避免使用 PostgreSQL 数组类型；多值文本优先用普通 `TEXT` 保存展示值，确需结构化时使用 `JSONB` 并在服务层做校验。

DDL 落地约定：

- 主键统一使用 `BIGSERIAL`，固定小字典表可使用 `SMALLSERIAL`。
- `created_at`、`updated_at` 默认 `now()`；更新 `updated_at` 可由服务层统一写入，暂不强制使用数据库触发器。
- 业务状态字段、编号字段、核心外键和标题类必填字段在建表时加 `NOT NULL`；确实允许系统任务、匿名访问或多态附件的字段再放开为空。
- 枚举字段建议加 `CHECK` 约束，约束值与本文档英文枚举保持一致。
- 关系明确的字段建立外键；`business_attachments`、`audit_logs` 等多态业务对象表不建跨表外键，由服务层按 `business_type + business_id` 校验目标对象存在。
- 所有 partial unique index 必须写入 Flyway 迁移脚本，不能只依赖服务层判断。

### 2.4 清单状态展示映射

数据库统一保存英文枚举，前端按来源类型和状态映射为中文展示。接口返回可同时返回 `status` 和 `statusText`，但后端判断只使用英文枚举。

| 对象 | 英文枚举 | 移交展示 | 征集展示 | 说明 |
|------|----------|----------|----------|------|
| 清单批次 | `draft` | 草稿 | 草稿 | 提交前可编辑 |
| 清单批次 | `pending_transfer` | 待移交 | - | 移交单位已提交，等待线下交接 |
| 清单批次 | `pending_contact` | - | 待联系 | 公众已提交捐赠意向，等待后台联系 |
| 清单批次 | `pending_receive` | - | 待接收 | 已约定到馆时间，等待前台验收 |
| 清单批次 | `received` | 已接收 | 已接收 | 全部条目验收通过 |
| 清单批次 | `partially_received` | 部分接收 | 部分接收 | 部分条目接收，部分条目回退 |
| 清单批次 | `rejected` | 已回退 | 已拒绝 | 移交侧表示整批回退；征集侧表示整批拒绝 |
| 清单批次 | `archived` | 已入库 | 已入库 | 已接收条目全部生成正式档案 |
| 清单批次 | `shelved` | 已上架 | 已上架 | 纸质相关档案上架完成；纯电子批次不使用该状态 |
| 清单条目 | `draft` | 草稿 | 草稿 | 随清单提交前可编辑 |
| 清单条目 | `pending_acceptance` | 待验收 | 待验收 | 等待前台验收 |
| 清单条目 | `accepted` | 已接收 | 已接收 | 条目验收通过 |
| 清单条目 | `rejected` | 已回退 | 已回退 | 条目验收不通过 |
| 清单条目 | `pending_archive` | 待入库 | 待入库 | 条目等待后台入库 |
| 清单条目 | `archived` | 已入库 | 已入库 | 条目已生成正式档案 |

说明：批次不再单独保存 `pending_archive`。后台“待入库”列表按批次 `received`、`partially_received` 且存在未入库的已接收条目计算；条目级 `pending_archive` 表示该条目已完成 AI/人工确认，等待正式入库。纯电子批次在已接收条目全部入库后停留在 `archived`，不展示上架按钮；只有包含纸质相关档案的批次在实物确认上架后进入 `shelved`。

- 小张、小李、小陈、小刘、小方、系统管理员均使用 `users` 表，通过角色区分。

| `carrier_status` | VARCHAR(20) | 纯电子、纸质+电子、纯纸质 |
| `retention_period` | VARCHAR(20) | `10y`、`30y`、`permanent` |
| `retention_until` | DATE | 到期日；永久为空 |
| `security_level` | SMALLINT | 0-4 |
| `open_status` | VARCHAR(20) | `open`、`closed` |
| `allow_digitization` | BOOLEAN | 是否允许数字化 |
| `lifecycle_status` | VARCHAR(30) | `pending_shelf`、`normal`、`pending_destruction`、`destroyed` |
| `loan_status` | VARCHAR(20) | `available`、`on_loan` |
| `condition_status` | VARCHAR(20) | `normal`、`damaged`、`repairing`、`lost`、`destroyed` |
| `archived_at` | TIMESTAMPTZ | 入库时间 |
| `shelved_at` | TIMESTAMPTZ | 上架时间；纯电子可为空 |

业务规则：

- 移交/征集清单不是正式档案，只有后台确认入库才写入 `archives`。
- 纯电子档案入库后 `lifecycle_status = normal`。
- 纸质+电子和纯纸质档案入库后先为 `pending_shelf`，点击已上架后才变为 `normal`，才进入查阅检索和借阅范围。
- `10y` 和 `30y` 保管期限从 `archived_at` 起算并写入 `retention_until`；`permanent` 的 `retention_until` 为空。鉴定延长保管期限时，从当前日期重新计算新的到期日。
- 公众检索固定过滤：`security_level = 0 AND open_status = 'open' AND lifecycle_status = 'normal'`。
- 内部查阅不按 `open_status` 硬过滤；`open_status` 只控制公众开放范围。内部查阅按密级上限、数据范围和档案生命周期过滤。
- `archive_no`、`security_level`、`retention_period`、`open_status`、`allow_digitization`、架位和销毁状态为受保护字段，不能由普通元数据编辑或 AI 补全直接覆盖。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGSERIAL | 主键 |

| `scan_result` | VARCHAR(20) | `pending`、`safe`、`infected`、`failed` |
| `scan_message` | TEXT | 病毒扫描说明或失败原因 |
| `check_summary` | JSONB | 四性检查摘要 |
| `uploaded_by` | BIGINT | 前台上传人 |
| `uploaded_at` | TIMESTAMPTZ | 上传时间 |

业务规则：

- 移交单位和公众侧拖拽不写入 `staging_files`，只在浏览器本地解析文件名。
- 前台管理员上传后才写入 `staging_files`。
- 上传阶段必须完成格式、大小、哈希、MIME 和 ClamAV 检查，只有 `scan_result = 'safe'` 的文件才能写入 MinIO 暂存路径并进入后续匹配。ClamAV 不可用、扫描超时、扫描失败或命中病毒时，本次上传失败，不创建 `staging_files` 记录和可用暂存对象；失败原因只写入 `audit_logs`。
- 入库成功后，暂存对象复制为正式对象，写入 `archive_files`，再将 `match_status` 置为 `archived`。
- 前台验收回退已上传电子文件的条目时，立即物理删除 MinIO 暂存对象，但保留 `staging_files` 记录，将 `match_status` 置为 `deleted` 并写入 `audit_logs`。
- 暂存对象路径使用 `staging_files.id` 保证跨批次唯一，格式为 `archive-files/_staging/{sourceType}/{batchId}/{stagingFileId}/{fileName}`；`upload_batch_no` 只标识一次拖拽上传批次，同批多个文件共享该值。未匹配文件允许 `item_id` 为空，因此暂存路径不能依赖清单条目 ID。
- 暂存转正式采用“先插正式文件记录、再复制对象、最后更新状态”的补偿口径：先创建 `archive_files` 记录并取得 `archive_files.id`，初始 `file_status = pending`，正式路径使用 `archive-files/{archiveNo}/{archiveFileId}/{fileName}`；MinIO 复制成功后更新 `archive_files.file_status = normal` 和 `staging_files.archived_file_id`。若复制失败，保留 `archive_files` 记录并将 `file_status = failed`，后台可重试暂存转正式。

- 审批通过不等于出库；只有填写 `checked_out_at` 后档案 `loan_status` 才变为 `on_loan`。
- 首次导出凭证时生成 `voucher_no` 并写入 `voucher_issued_at`，申请状态从 `approved` 变为 `voucher_issued`；重复导出复用原凭证号。PDF 可即时流式返回，若业务要求留存，则挂到 `business_attachments`，`business_type = borrow_request`，`attachment_type = borrow_voucher_pdf`。

- 逾期不作为常规落库状态更新。个人工作台、后台概览、借阅审批/当前借阅列表查询时，对 `status = 'checked_out' AND due_at < now()` 的记录动态返回 `overdue = true` 和展示状态「逾期」。归还仍将状态改为 `returned` 或 `abnormal_return`。

## 13. 关键关系

### 13.1 清单到正式档案

```text
intake_batches
  └── intake_items
        ├── staging_files
        └── archives.generated from intake_items
              ├── archive_files
              ├── archive_tags
              └── archive_box_items
```

要点：

- 清单条目和正式档案是两个阶段，不能提前占用档号。
- `intake_items.generated_archive_id` 用于追踪“这条清单最终生成了哪份档案”。
- 移交/征集档案通过 `archives.source_batch_id`、`source_item_id` 反查来源清单和条目。
- 编研成果档案通过 `archives.source_compilation_id` 反查来源编研成果，不复用清单来源字段。

### 13.2 纸质位置

```text
warehouse_rooms
  └── storage_locations
        └── archive_boxes
              └── archive_box_items
                    └── archives
```

要点：

- 架位绑定档案盒，不直接绑定档案。
- 一个盒内可以放多份档案。
- 纸质档案上架前不进入查阅和借阅范围。
- 架位占用关系以 `archive_boxes.location_id` 为单一事实来源，不在 `storage_locations` 再保存当前盒号。纸质档案入库时即绑定档案盒和架位，确认上架只更新档案状态；移位、下架、整盒腾空只需要更新档案盒的 `location_id` 和 `status`，空架位通过查询计算。

### 13.3 审批

```text
approval_requests
  ├── target archive / destruction_list
  └── evidence_archive_id
```

要点：

- 密级调整、开放调整使用同一张审批表，`evidence_archive_id` 记录凭证档案。
- 销毁审批目标是销毁清册。
- 审批通过后才修改目标业务表。

### 13.4 销毁

```text
appraisal_batches
  └── appraisal_items
        └── destruction_lists
              └── destruction_items snapshot
```

要点：

- 鉴定为待销毁后自动生成销毁清册。
- 清册明细保存档号、题名、密级、保管期限等快照。
- 确认销毁只改变档案状态和文件状态，不删除档案元数据；纸质档案确认销毁后解除 `archive_box_items` 盒内关系并更新 `archive_boxes.used_count`，销毁追溯以 `destruction_items` 快照、审批和审计日志为准。

### 14.4 业务约束

| 约束 | 实现建议 |
|------|----------|
| 公众只能看公开档案 | 后端强制追加 `security_level = 0 AND open_status = 'open' AND lifecycle_status = 'normal'` |
| 内部查阅按密级和范围过滤 | 后端按 `max_security_level`、`organization_id`、`fonds_id` 拼查询条件，并固定要求 `lifecycle_status = 'normal'`；内部查阅不按 `open_status` 硬过滤，`open_status` 只控制公众开放；`data_scope = own_fonds` 时按 `users.organization_id` → `fonds.organization_id` 找到 `fonds_id` 列表，再过滤 `archives.fonds_id IN (...)` |
| 纸质档案上架前不可借阅 | 借阅申请校验 `lifecycle_status = 'normal'`、`loan_status = 'available'`、`condition_status = 'normal'`，并且未命中运行中的盘点任务 |
| 销毁档案不可恢复 | `lifecycle_status = 'destroyed'` 后禁止普通更新 |
| AI 不覆盖受保护字段 | AI 结果只写 `ai_suggestion` 或 `analysis_items.suggestion` |
| 凭证档号必须存在 | 审批提交时按 `archives.archive_no` 查证据档案 |
| 清单部分接收 | 批次状态由条目状态汇总，回退条目不入库 |
| 征集数量限制 | 服务层按 `intake_batches` 统计当前公众待处理和拒绝清单数量；默认待处理上限 5 个、单清单 200 条、待处理加已拒绝合计上限 10 个，具体从 `system_configs` 读取；超过上限时拒绝新建并提示联系管理员，本期不自动删除历史清单 |
| 防重复借阅 | 对 `borrow_requests.archive_id` 建 partial unique index，限制 `status IN ('applied','approved','voucher_issued','checked_out')`；`abnormal_return` 是借阅终态，后续借阅由档案 `condition_status` 拦截；逾期由 `checked_out + due_at < now()` 动态判断 |
| 防重复审批 | 对 `approval_requests(approval_type, target_type, target_id)` 建 partial unique index，限制 `status = 'pending'` |
| 防重复入库 | `intake_items.generated_archive_id` 非空唯一，且写入后不可改到另一份档案 |
| 来源字段一致性 | `archives.source_type IN ('transfer','collection')` 时必须填写 `source_batch_id`、`source_item_id`，且 `source_compilation_id` 为空；`source_type = 'compilation'` 时必须填写 `source_compilation_id`，且 `source_batch_id`、`source_item_id` 为空 |
| 征集字段一致性 | `intake_batches.source_type = 'collection'` 时必须填写 `public_user_id`，提交时必须填写 `agreement_accepted_at`；`source_type = 'transfer'` 时必须填写 `organization_id` |
| 载体字段一致性 | `carrier_status = 'electronic'` 不允许写入 `archive_box_items`；`carrier_status IN ('paper_electronic','paper')` 入库时必须写入档案盒关系并预占架位；`carrier_status = 'paper'` 不应创建 `archive_files.file_role IN ('original','scan')`，除非后续数字化后按扫描件流程补充 |
| 扫描通过才能入库 | 接收上传必须先完成 ClamAV 扫描，只有 `scan_result = 'safe'` 的暂存文件才能标记为 `matched` 并转正式；ClamAV 不可用、超时或失败时拒绝上传 |

### 14.5 并发与事务口径

以下流程会同时修改多张表，服务层必须使用数据库事务，并对关键行加锁或使用乐观锁字段，避免并发操作造成重复入库、重复占位或状态回退。

| 流程 | 并发控制建议 |
|------|--------------|
| 清单提交、验收、回退 | 锁定 `intake_batches` 和本次更新的 `intake_items`；所有条目更新后统一调用批次状态重算逻辑 |
| AI 补全任务创建与重试 | 锁定 `intake_batches.latest_ai_task_id` 或按 `ai_tasks.business_type + business_id` 校验运行中任务，避免同一批次同时启动多个补全任务 |
| 确认入库 | 锁定目标 `intake_items`、目标 `archive_boxes` 和相关 `storage_locations`；生成 `archives`、`archive_files`、`archive_box_items` 与回写 `generated_archive_id` 必须同事务提交 |
| 档案盒占位与移位 | 依赖 `archive_boxes.location_id` 的 partial unique index，同时在选择空架位后锁定对应 `storage_locations` 行 |
| 借阅申请、审批、出库、归还 | 借阅申请依赖 partial unique index 防重复；审批和出库前锁定 `archives` 行并重新校验 `loan_status`、`condition_status` 和盘点范围 |
| 鉴定与销毁清册生成 | 锁定鉴定批次和命中的 `archives`；生成 `destruction_items` 快照后，不再从档案主表回填销毁清册展示字段 |
| 确认销毁 | 锁定 `destruction_lists`、`destruction_items` 和对应 `archives`；文件删除、档案状态、盒内关系解除和审计日志必须作为一个业务事务处理，MinIO 删除失败时记录失败状态并允许后台补偿 |

批次状态重算必须集中在服务层一个方法中实现，接口不得分别手写批次状态判断。推荐口径：条目全部 `archived` 时批次为 `archived`；存在已接收但未入库条目时批次保持 `received` 或 `partially_received`；存在回退条目且仍有已接收条目时为 `partially_received`；全部回退时为 `rejected`。
